# 구매에서 지급까지, 어디서 시간이 걸리나: P2P 프로세스 병목 분석

회사가 물건을 사고 돈을 내기까지 어느 단계에서 시간이 가장 오래 걸리는지, 도료 제조사의 실제 구매 기록 21만 건으로 분석했습니다.

- 물건은 9일, 송장은 8일이면 처리되는데 대금 지급에는 43일이 걸렸습니다. 10건 중 1건은 98일 넘게 걸렸습니다.
- 가장 늦게 지급된 1.7만 건 중 90%가 포장재(Packaging) 공급사 5곳에 몰려 있었습니다.
- 전체 공급사를 다 볼 필요 없이, 이 5곳의 결제 조건과 지급 일정부터 점검하면 지연 대부분을 다룰 수 있습니다.

| 핵심 수치 | 값 |
|---|---|
| 가장 오래 걸리는 단계 | 송장 접수 → 대금 지급, 보통 43일 (가장 오래 걸린 10%는 98일 이상) |
| 지연이 몰린 곳 | 늦게 지급된 17,165건 중 15,400건(89.7%)이 포장재 공급사 5곳 |
| 가장 심한 공급사 | 거래 품목의 73%가 늦게 지급됨 (전체 평균 10%) |

보고서: [요약 6장](reports/P2P_분석보고서_v0.1_요약.pdf) · [전체 16장](reports/P2P_분석보고서_v0.1.pdf)

### 내가 한 일

- 문제 정의: "어디서 늦는가"를 측정 가능한 질문과 가설 5개로 바꾸고, 지연의 기준을 정함
- 데이터 품질 기준 수립: 1948년 같은 불가능한 날짜, 중복 기록, 순서가 뒤집힌 기록을 찾아 처리 규칙을 정함
- 검증: 핵심 수치를 서로 다른 두 방법으로 다시 계산하고, 실제 기록 한 건을 열어 계산값과 대조함

---

## 1. 왜 이 질문인가

구매에서 지급까지는 발주 → 입고 → 송장 접수 → 대금 지급 순서로 진행됩니다. 지급이 늦어지면 공급사와의 신뢰, 자금 계획, 조기 결제 할인 같은 조건에 영향을 줍니다.

그런데 실무 담당자는 건별로 처리하기 때문에, 전체 흐름에서 어느 단계가 막히는지는 잘 보이지 않습니다. 그래서 질문을 이렇게 정했습니다.

> 발주부터 지급까지 어느 단계에서 지연이 생기고, 그 지연은 어떤 공급사에 몰려 있는가?

이 질문을 다섯 가지 가설로 나눠 하나씩 확인했습니다.

| | 가설 | 결과 |
|---|---|---|
| H1 | 지연은 특정 단계에 몰려 있다 | 맞음: 송장 접수 → 지급 |
| H2 | 지연은 소수 공급사에 몰려 있다 | 맞음: 포장재 공급사 5곳이 89.7% |
| H3 | 거래가 많은 공급사라서 지연도 많다 | 아님: 거래량이 비슷해도 지연 비율이 2배 이상 차이 |
| H4 | 지급 보류가 지연의 원인이다 | 일부만 맞음: 보류만으로는 설명 부족 |
| H5 | 아직 지급되지 않은 건은 취소·변경·누락·진행 중으로 나뉜다 | 대부분 진행 중(75.5%), 삭제·취소 17.4% |

## 2. 어떤 데이터인가

- 네덜란드 도료·코팅 제조사의 2018년 구매 기록을 익명화한 공개 데이터 (BPI Challenge 2019)
- 이 중 "송장이 입고보다 먼저 와도 되는" 거래 방식 품목만 담긴 부분집합 사용 (Zenodo record 17295283, 원본의 86%)
- 구성: 품목 표(217,406행)와 활동 기록 표(1,214,244행). 품목 하나에 발주·입고·송장·지급 같은 활동이 평균 5.6건 기록됨
- 기간: 2018년 1월 ~ 2019년 1월

| 표 | 한 줄의 의미 | 분석에 쓴 칸 |
|---|---|---|
| cases | 발주서의 품목 한 줄 | case_id(품목 번호), vendor(공급사), spend_area_text(지출 영역) |
| events | 활동 한 번 | case_id, activity(무슨 일), ts(언제) |

## 3. 어떻게 분석했나

각 단계에서 무엇을 재고, 기준은 왜 그렇게 정했고, 어떻게 확인했는지 정리했습니다.

| 질문 | 무엇을 쟀나 | 기준과 이유 | 어떻게 확인했나 | 결과 |
|---|---|---|---|---|
| 데이터를 믿을 수 있나 | 불가능한 날짜, 중복, 순서가 뒤집힌 기록 | 1948년 같은 날짜가 있는 품목은 통째로 빼지 않고 그 날짜만 제외. 통째로 빼면 발주→지급 기록이 정상인 품목까지 빠지기 때문 | 해당 품목의 실제 기록을 열어 확인 | 지급까지 끝난 172,241품목을 분석 대상으로 확정 |
| 어느 단계가 오래 걸리나 | 단계별 소요일 | 같은 활동이 여러 번이면 첫 시각 기준. 대표값은 평균 대신 중앙값(보통 며칠)과 가장 오래 걸린 10%의 경계(P90). 아주 긴 몇 건이 평균을 끌어올리기 때문 | 순서가 뒤집힌 9건을 빼도 중앙값이 같은지 확인 | 송장 접수 → 지급이 병목 |
| 지연은 누구에게 몰렸나 | 공급사별 지연 비율 (그 공급사 품목 중 늦게 지급된 비율) | "늦은 지급" = 송장 접수 후 98일 초과(가장 오래 걸린 10%). 우선 점검 대상 = 지연 비율이 평균의 3배(30%) 이상 | 건수와 비율을 함께 봐서 "거래가 많아서 많아 보이는 것"을 걸러냄 | 포장재 공급사 5곳 |
| 지급 보류 때문인가 | 보류 해제 기록이 있는 비율 | 늦은 건과 늦지 않은 건을 비교 (비교 대상이 없으면 높은지 낮은지 판단 불가) | 보류를 건 기록은 52건뿐이라 해제 기록으로 간접 판단한다는 한계를 명시 | 57.9% vs 42.5%, 차이가 작아 주원인은 아님 |
| 아직 지급 안 된 건은 어떤 상태인가 | 마지막 활동과 마지막 시각 | 데이터 마지막 날로부터 98일 이내면 "진행 중". 늦은 지급 기준과 같은 숫자로 맞춤 | 기준을 한 달 바꿔도 결론이 같은지 확인 | 75.5%가 진행 중, 그중 다수가 송장 접수 후 지급 대기 |

## 4. 결과와 제안

- 물건과 송장은 각각 9일, 8일 안팎에 처리되지만, 송장 접수 후 대금 지급까지 보통 43일이 걸림
- 늦게 지급된 건의 89.7%가 포장재 공급사 5곳(0136, 0103, 0278, 0120, 0182)에 집중
- 거래 품목 수가 거의 같은 두 공급사도 지연 비율은 73.2%와 33.6%로 2배 이상 차이. 거래량 문제가 아니라 공급사별 조건이나 절차 차이일 가능성

제안
- 지급 담당 부서가 이 5곳의 결제 조건과 지급 일정을 먼저 확인
- "송장 접수 후 98일 초과"를 지연 기준으로 고정하고, 공급사별 지연 비율을 매달 같은 방식으로 확인. 이번 분석 SQL을 그대로 월별 점검에 사용 가능

## 5. 결과를 어떻게 확인했나

| 확인 방법 | 사례 | 결과 |
|---|---|---|
| 같은 숫자를 다른 방법으로 다시 계산 | 아직 지급 안 된 품목 수를 두 가지 쿼리로 계산 | 둘 다 44,594건 |
| 실제 기록을 열어 대조 | 1위 공급사의 품목 하나(4508044951_00020) | 송장 접수 8/9 → 지급 12/7, 계산값 119.9일과 일치 |
| 처리 규칙을 데이터로 재검토 | "이상 날짜가 있는 품목 193개를 통째로 제외"하는 안을 검토 → 예시 품목은 발주→지급이 정상 | 날짜만 제외하는 규칙으로 변경 |
| 예외 기록이 결론을 바꾸는지 | 지급이 송장보다 먼저 기록된 9건을 빼고 다시 계산 | 중앙값 42.99일로 동일 |
| 기준을 바꿔도 결론이 같은지 | "진행 중" 기준을 한 달 늦춰 다시 계산 | 75.5% → 83.0%, 결론 동일 |
| 처음부터 다시 실행 | 명령 한 줄로 모든 쿼리 재실행 | 기록해 둔 수치와 모두 일치 |

SQL 일부는 AI 도구로 초안을 만든 뒤 위 방법으로 결과를 확인하고 채택했습니다. 질문, 측정 기준, 판단 기준, 결론은 직접 정했습니다.

## 7. 직접 실행해 보기

```bash
# 1) 데이터 적재 (최초 1회, Zenodo 17295283의 XES 파일 필요)
python src/load.py data/raw/zenodo_17295283/BPIC19_3way_IbeforeGR_standardPO_complete.xes data/p2p.duckdb

# 2) 분석 전체 실행 (읽기 전용, my_sql/01~06 순서대로)
python src/run_my_sql.py
```

| 경로 | 내용 |
|---|---|
| `my_sql/01~02` | 데이터 이해, 품질 점검 |
| `my_sql/03~04` | 측정 기준 정의, 단계별 소요일 |
| `my_sql/05~06` | 지연이 몰린 공급사, 미지급 건 상태 분류 |
| `notes/my_01~04` | 단계별 질문, 결정, 결과, 한계 기록 |
| `reports/` | 보고서 PPT·PDF (요약 6장, 전체 16장) |
| `src/load.py` | 원본 데이터(XES) → DuckDB 적재 |
| `src/run_my_sql.py` | 분석 SQL 전체 실행 |

환경: Python 3, DuckDB (`pip install duckdb`)
