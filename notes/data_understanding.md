# 데이터 이해 메모

> 이 데이터를 처음 보는 사람이 5분 안에 "무엇을 기록한 데이터이고, 어디까지 믿고 쓸 수 있는지" 알 수 있게 정리한 문서다.
> 1~3절은 흐름 이해용, 4~5절은 숫자와 주의점, 6절은 찾아보는 사전이다.

## 한눈에 보기

- **무엇:** 한 다국적 제조사(도료·코팅)가 2018년에 물건을 **주문하고, 받고, 청구서를 받고, 돈을 낸** 과정 전체의 기록
- **규모:** 주문 품목 217,406건, 그 품목들에 일어난 일 1,214,244건
- **단위:** 기록 1건은 "어떤 품목에, 언제, 누가, 무엇을 했나"

---

## 1. 이 데이터는 무엇을 기록했나

회사가 물건을 사는 과정은 온라인 쇼핑과 비슷하다. 다만 회사는 **물건과 청구서를 확인한 다음에** 돈을 낸다.

```
  ① 주문          ② 물건 도착       ③ 청구서 도착       ④ 돈 지급
  (발주, PO)  →   (입고, GR)   →   (송장, IR)    →   (지급)
  구매팀           창고·현장          재무팀             재무팀
```

- 회사는 ①②③ **세 가지가 서로 맞는지**(수량·금액) 확인한 뒤에 ④ 돈을 낸다. 이 확인 절차를 **3-way 매칭**이라고 한다.
- 이 데이터는 위 과정의 각 단계가 일어날 때마다 **언제, 누가, 얼마**를 남긴 시스템 기록이다.
- 이 데이터를 받아 둔 버전(Zenodo 부분집합)은 그중 **"청구서가 물건보다 먼저 와도 되는"** 흐름(3-way, invoice before GR)만 담고 있다. 그래서 ②와 ③의 순서가 바뀐 품목이 있다.

## 2. 실제 기록 한 건: 포장용 라벨 208유로어치

품목 `4507000221_00010` (발주서 4507000221의 10번 줄). 공급업체 `vendor_0103`, 포장재 > 라벨.

| 언제 (UTC) | 무슨 일 | 누가 |
|---|---|---|
| 1/1 02:42 | 주문 생성 | 자동 시스템 (batch_03) |
| 1/2 10:04 | 공급업체가 주문 확인 | user_029 |
| 1/5 12:36 | 물건 도착 | user_030 |
| 1/5 16:35 | 회사가 청구서 접수 | user_024 |
| 1/5 22:59 | 공급업체가 청구서 발행 | 기록 없음 (NONE) |
| **4/26** 09:14 | 돈 지급 | user_002 |

읽는 법:
- 주문부터 물건 도착까지 4일, 청구서를 받고 돈을 내기까지 **111일**이 걸렸다.
- "청구서 접수"가 "청구서 발행"보다 몇 시간 먼저 찍혀 있다. 이런 어색한 점을 찾고 원인을 따지는 것이 분석의 출발점이다(5절).

## 3. 데이터의 생김새

```
cases (품목 1건 = 1줄, 217,406줄)          events (일어난 일 1건 = 1줄, 1,214,244줄)
┌────────────────────────────┐          ┌──────────────────────────────────┐
│ case_id  ← 품목 번호        │ 1 ──── N │ case_id                          │
│ 공급업체, 품목군, 품목 유형 … │          │ activity (무슨 일)                 │
└────────────────────────────┘          │ ts (언제) · resource (누가)        │
                                        │ net_worth_eur (그때 품목 금액)      │
                                        └──────────────────────────────────┘
```

- **cases** = 품목의 **변하지 않는 정보**(누구에게 무엇을 샀나)
- **events** = 품목에 **일어난 일의 순서**(언제 무엇이 일어났나)
- 품목 하나에 평균 5~6개의 일이 기록돼 있다.
- 파일 위치: `data/p2p.duckdb`. 원본 XES 파일에서 `src/load.py`로 만든다.

## 4. 데이터로 확인한 사실

표기: ✅ 데이터로 확인함 · ❓ 추정, 아직 확인 안 함

| 사실 | 숫자 | 의미 | 상태 |
|---|---|---|---|
| 적재 중 빠진 건 없음 | 원본 파일과 DB 건수 일치 (217,406 / 1,214,244) | 이 DB를 원본 대신 써도 된다 | ✅ |
| 회사는 사실상 1곳 | companyID_0000 217,404건, 다른 회사 2건 | 회사끼리 비교는 불가. 한 회사 내부 분석이다 | ✅ |
| 공급업체는 다양함 | 1,310곳 | 공급업체별 비교는 가능 | ✅ |
| 품목군도 다양함 | 대분류 19개, 소분류 114개 | 무엇을 샀는지별 비교 가능 | ✅ |
| 담당자 | 571명(자동 시스템 포함) | 사람·자동 처리 비교 가능 | ✅ |
| 흐름은 1종류 | item_category 값이 전부 "3-way, invoice before GR" | 부분집합 정의와 일치. 흐름 간 비교는 원본이 필요 | ✅ |
| 발주 문서 종류 2개 | Standard PO 외에 Framework order가 섞여 있음 | 파일 이름은 "standard PO"인데 다른 값이 있음. 건수 확인 필요 | ✅ / 건수 ❓ |
| 같은 발주서의 품목은 같이 움직이는 경우가 많음 | 10건 샘플에서 확인 | "품목 기준"으로 셀지 "발주서 기준"으로 셀지 정해야 한다 | 샘플만 ✅ |
| 이름이 숨겨져 있음 | 회사·공급업체·담당자가 `companyID_0000`, `vendor_0103`, `user_029` 식 | 실제 데이터를 익명화한 것. 값 0000은 "빈칸"이 아니라 이름표 | ✅ |

## 5. 알고 써야 할 주의점

| 주의점 | 무엇이 문제인가 | 어떻게 다루나 |
|---|---|---|
| 흐름이 1종류뿐 | 원본의 4가지 흐름 중 하나만 있다 | 결론은 "이 흐름 안에서"로 한정해서 말한다 |
| 회사가 1곳 | 일반화할 수 없다 | "이 회사의 2018년 구매 과정"까지만 말한다 |
| **"왜"가 기록돼 있지 않음** | 지급 보류를 **푼** 기록은 54,458건인데 **건** 기록은 52건뿐. 멈춘 사유가 없다 | 원인은 직접 확인할 수 없다. 공급업체·품목군 분포로 간접적으로 본다 |
| 시간대 | 원본은 UTC인데 DBeaver는 한국 시간(+9시간)으로 보여 준다 | 날짜별로 셀 때 하루가 밀릴 수 있다. 계산은 UTC 기준으로 한다 |
| 빈 문자열 | 품목군 컬럼 일부가 NULL이 아니라 빈 글자("")로 들어 있다 | 빈 값 비율 통계(null_percentage)에 잡히지 않는다. 따로 세야 한다 |
| 이상한 시각 | 가장 이른 시각이 1948년 | 2018년 이전 시각이 있는 193건(0.1%)은 분석에서 뺀다 |
| 컬럼·활동 설명이 추정 | 6절 설명은 Claude가 기억으로 정리했다 | 4TU 공식 설명이 열리면 대조해서 ❓를 고친다 |
| 숫자 개수는 근사값 주의 | DuckDB `SUMMARIZE`의 고유값 개수(approx_unique)는 추정치다 | 정확한 숫자는 `count(DISTINCT …)`로 다시 센다 |

## 6. 사전 (찾아볼 때)

### 6-1. 용어

| 용어 | 뜻 |
|---|---|
| 발주 (PO, Purchase Order) | 회사가 공급업체에 보내는 주문서 |
| 입고 (GR, Goods Receipt) | 주문한 물건이 도착해서 받았다고 기록하는 것 |
| 송장 (IR, Invoice Receipt) | 공급업체가 보낸 청구서를 회사가 받았다고 기록하는 것 |
| 3-way 매칭 | 발주·입고·송장 세 가지의 수량과 금액이 맞는지 확인한 뒤 지급하는 규칙 |
| 케이스 | 분석 단위. 이 데이터에서는 **발주서 한 장이 아니라 그 안의 품목 한 줄** |
| 활동 (activity) | 케이스에 일어난 일 하나 (예: 물건 도착) |
| variant (변형) | 활동 순서가 완전히 똑같은 케이스들의 묶음 |
| 부분집합 | 원본 전체에서 조건에 맞는 것만 골라낸 데이터 |

### 6-3. `cases` 컬럼 (품목 정보)

| 컬럼 | 뜻 | 확인한 값 | 상태 |
|---|---|---|---|
| `case_id` | 품목 번호. `발주서번호_줄번호` | 217,406개 | ✅ |
| `purchasing_document` | 발주서 번호 | 약 6.4만 개 | 뜻 ❓ |
| `item` | 발주서 안의 줄 번호 (00010, 00020 …) | | ❓ |
| `company` | 주문한 자회사 (익명) | 사실상 1개 | ✅ |
| `vendor` | 공급업체 번호 (익명) | 1,310개 | ✅ |
| `name` | 공급업체 이름 (익명) | 개수가 vendor보다 적음 → 1:1인지 확인 필요 | ❓ |
| `document_type` | 발주 문서 종류 | Standard PO, Framework order | ✅ |
| `purch__doc__category_name` | 구매 문서 범주 | 전부 Purchase order | ✅ |
| `item_type` | 품목 유형 | 3종 (Standard, Third-party 등) | ✅ |
| `item_category` | 매칭 흐름 | 전부 "3-way match, invoice before GR" | ✅ |
| `spend_area_text` | 무엇을 샀나 (대분류, 예: Packaging) | 19개 + 빈 글자 | ✅ |
| `sub_spend_area_text` | 무엇을 샀나 (소분류, 예: Labels) | 114개 + 빈 글자 | ✅ |
| `spend_classification_text` | 지출 분류 코드 (예: PR) | 몇 종 + 빈 글자. 뜻 모름 | ❓ |
| `source` | 원천 시스템 | 전부 1개 | ✅ |
| `gr_based_inv__verif` | 입고가 있어야 청구서를 확인할 수 있는가 | 전부 false | ✅ |
| `goods_receipt` | 입고가 필요한 품목인가 | 전부 true | ✅ |

- `gr_based_inv__verif` = false(입고 없이도 청구서 확인 가능)와 `goods_receipt` = true(입고는 필요)의 조합이 "청구서가 물건보다 먼저 와도 되는" 흐름의 정의와 맞는 것으로 보인다. ❓
- 이 표의 값은 전부 글자(VARCHAR)로 저장돼 있다. true/false도 글자다.

### 6-4. `events` 컬럼 (일어난 일)

| 컬럼 | 뜻 | 상태 |
|---|---|---|
| `case_id` | 어느 품목의 일인가 | ✅ |
| `activity` | 무슨 일인가 (6-2 참고) | ✅ |
| `ts` | 언제. UTC로 저장, DBeaver에는 한국 시간으로 보임 | ✅ |
| `net_worth_eur` | 그 시점의 품목 금액(유로, 누적) | ❓ |
| `resource` | 누가. `batch_*`는 자동 처리, `NONE`은 기록 없음 | ❓ |
| (적재 안 함) `User` | 첫 케이스에서는 resource와 같았음. 전체에서도 같은지 확인 필요 | ❓ |
